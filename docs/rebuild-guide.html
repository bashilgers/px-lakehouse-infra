Build guide Architecture

px-lakehouse: build from zero

This guide gives the order to build the px-lakehouse platform from nothing, and to tear it down. Each plan runs one time. No step between the plans needs a code change or a manual action.

1. Build order

Apply the plans in this order, one apply each. A plan finds what the plans before it made by name. Thus you do not copy IDs between the plans.

2. Commands

The full build, from the repository root. Section 4 explains each step.

export TF_VAR_azure_client_id="" TF_VAR_azure_client_secret=""
export ARM_TENANT_ID=d782e4c4-3c47-405e-9ac6-7b76e8f4eb97

plans/terraform_state/bootstrap.sh                 # 1. first time only; later: init and apply
for p in user_management unity_catalog_metastore; do  # 2. and 3.
  terraform -chdir=plans/$p init && terraform -chdir=plans/$p apply
done
for env in dev test prod; do                       # 4. in parallel, about 8 minutes
  (terraform -chdir=plans/$env init && terraform -chdir=plans/$env apply -auto-approve) &
done; wait

# 5. in px-lakehouse-data (its docs/build-guide.html): per environment, scripts/sql-access.sh,
#    then one CI run (Actions > databricks-infra > Run workflow). Each waits on its script.
for env in dev test prod; do scripts/sql-access.sh $env; done
for env in dev test prod; do gh workflow run databricks-infra.yml --ref main -f environment=$env; done

To tear down, after px-lakehouse-data's objects:

for env in dev test prod; do scripts/teardown-environment.sh $env; done
terraform -chdir=plans/unity_catalog_metastore destroy
terraform -chdir=plans/user_management destroy

3. Before you start

  • Log in with az login. Your account must be Owner of the three subscriptions and a Databricks account admin. Step 4 also uses the Azure CLI to approve private endpoints.
  • Set these variables for every Terraform run. The plans then use your login, not a service principal.
export TF_VAR_azure_client_id="" TF_VAR_azure_client_secret=""
export ARM_TENANT_ID=d782e4c4-3c47-405e-9ac6-7b76e8f4eb97
  • Each provider copy is about 350 MB. Set TF_PLUGIN_CACHE_DIR to keep one copy for all plans.

6. Steps by hand

These steps stay manual on purpose. They handle secret values, or they need access that Terraform does not have. Do them between step 4 and step 5.

7. Tear down

Do the steps in reverse order.

  1. Data objects. Destroy px-lakehouse-data's objects in each environment first, one command each: scripts/teardown-environment.sh <env> in px-lakehouse-data. It lifts their guards for that run.
  2. Environments. Run one command per environment:
    scripts/teardown-environment.sh dev
    For this run only, the script writes an override file into the module. The file lifts prevent_destroy, opens the isolated credentials (else the destroy cannot delete them after their bindings) and lets the resource group go with what Azure added to it. The account still counts a deleted workspace for 5 to 11 minutes, and refuses to delete the network connectivity config while it does. Thus the script does the destroy again every 2 minutes until it is complete. At the end, it makes sure through the account API that the storage credential is gone: a credential delete that finds nothing passes silently. Add -auto-approve to run it without questions.
  3. Metastore. Run terraform destroy. Terraform cannot update the metastore (a provider error on the Delta Sharing token lifetime). If the metastore still holds objects, delete it with databricks account metastores delete <id> --force.
  4. Identities. Run terraform destroy. The Entra group members are not in the code: write them down first.
  5. State storage. Delete it last, by hand. It has prevent_destroy for this reason.

1. Where things live

Each environment has its own subscription with one resource group. The resource groups hold the same resources. Only the names and the address ranges are different. The prod subscription also holds the metastore storage and the Terraform state. Entra ID holds the groups and the app registrations. The Databricks account holds the metastore, and for each workspace its network objects.

One environment is drawn, and the two cards behind it are the other two. The three lines show what crosses a boundary: each workspace is assigned to the one metastore, the metastore keeps its root storage in the prod subscription, and the persona groups go from Entra ID into the Databricks account.

2. Network

Classic clusters run in the environment's VNet without public IP addresses. They reach the control plane through a private endpoint, and the internet through a NAT gateway. Serverless compute runs outside the VNet. It reaches the data through private endpoints from the NCC. People reach the workspace over the internet. The network policy lets in only two IP addresses and the deploy SP.

3. Access

People get access through groups only, never one by one. Jobs run as the run-as SP. CI deploys as the deploy SP. Neither people nor jobs hold an Azure role on the lake or on the SQL database. They hold Unity Catalog grants, and Unity Catalog reaches Azure for them.

Workspace settings

  • Personal access tokens are off. Nobody can make one. CI, Terraform and the CLI log in through Entra ID.
  • Git folders work only with repositories under https://github.com/bashilgers/.

  • An assignment to the workspace alone gives no access. Each persona group and the deploy SP get their own entitlements.

6. Points to know

  • The storage accounts and the key vaults accept traffic from any network. Only the Entra ID roles protect them. Shared keys are on for the environment storage accounts, but off for the state account.
  • Traffic out is open: from classic clusters through the NAT gateway, and from serverless (FULL_ACCESS).
  • The route table has no routes.
  • Data Factory has no pipelines and no network settings. The code marks this as to do.
  • The key vaults have no purge protection. A deleted vault is gone after 7 days.
  • Customer-managed keys are enabled on the workspaces, but no key is set.
  • The containers bronze, silver and gold are not used by Unity Catalog.
  • The members of the persona and key vault manager groups are not in the code. Write them down before a tear down.
  • The metastore has metastore-level storage. With it, Databricks makes a catalog main, open to every workspace, and the external location metastore_root_location, both owned by whoever made the metastore. A metastore without that storage would make neither: the catalogs have their own.
